# 实时通道选型结论与理由（REALTIME CHANNEL DECISION）

> 规格要求：「实时通道选型结论与理由（实时数据推送 vs 云托管 WebSocket）写入设计文档」。
>
> 本文件给出结论、对比矩阵、决策依据、风险与演进路径。

---

## 1. 结论

**第一阶段（本阶段）**：使用 `MockNetSyncService`（内存协议通道 + 本地权威裁判）。
此阶段不涉及真实网络，目的是**让协议与同步逻辑先跑通**。

**第二阶段（推荐选型）**：采用 **云数据库实时数据推送（`db.collection().watch()`）** 作为主通道，
辅以**云函数**做上行权威校验。即 `WxNetSyncService` 的默认实现方案。

**备选方案**：云托管 WebSocket。建议在出现以下任一情况时切换：
1. 对局要求严格时序（需要服务端主动 push 且延迟 < 100ms）；
2. 对局文档含敏感信息（如寻机头布局）且不希望下发客户端；
3. 单房间并发玩家数 > 2，且需要高频广播（watch 的增量推送在多人高频场景下会放大开销）。

## 2. 对比矩阵

| 维度 | 云数据库实时推送（watch） | 云托管 WebSocket | 评价 |
| :--- | :--- | :--- | :--- |
| **接入成本** | ⭐⭐⭐⭐⭐ 无需额外服务，`db.collection().watch()` 一行接入 | ⭐⭐ 需自建/托管容器、维护长连接、处理心跳与重连 | watch 显著占优 |
| **服务端代码量** | ⭐⭐⭐⭐ 云函数按需写，无状态 | ⭐⭐ 需实现连接管理、房间路由、断线检测 | watch 占优 |
| **延迟** | ⭐⭐⭐ 通常 200~500ms（数据库写 + 推送链路） | ⭐⭐⭐⭐⭐ 通常 30~100ms | WS 占优 |
| **时序保证** | ⭐⭐⭐ 最终一致，可能乱序/合并 | ⭐⭐⭐⭐⭐ 严格有序 | WS 占优 |
| **成本** | ⭐⭐⭐⭐ 按数据库读次数计费，本项目消息量小 | ⭐⭐ 容器常驻计费（即使无人对局） | watch 占优（小规模） |
| **运维复杂度** | ⭐⭐⭐⭐⭐ 免运维 | ⭐⭐ 需监控、扩缩容、日志排查 | watch 占优 |
| **连接数限制** | ⚠️ **每客户端最多 5 个 watch** | 无硬限制（受容器能力约束） | WS 占优 |
| **防作弊** | ⭐⭐⭐ 上行可走云函数校验，但**对局文档若可读则布局会泄露** | ⭐⭐⭐⭐⭐ 状态可完全保留在服务端 | WS 占优 |
| **断线重连** | ⭐⭐⭐ 自动重连但**只推增量**，必须配合全量对账 | ⭐⭐⭐⭐ 需自行实现重连 + 补发 | 各有优劣 |
| **微信生态契合** | ⭐⭐⭐⭐⭐ 官方一等公民，与云函数/云存储无缝 | ⭐⭐⭐ 云托管支持，但需额外配置 | watch 占优 |

## 3. 决策依据

### 3.1 为什么选 watch（本项目场景）

1. **对局消息量小、频率低**
   五子棋与寻机头都是**回合制**，人均操作间隔 0.8~2 秒（AI 思考时间），
   峰值 QPS 极低。延迟 200~500ms 对回合制游戏体验影响可忽略
   （对比：MOBA/FPS 类实时对战才需要 < 100ms）。

2. **零运维、零额外成本**
   watch 通过云开发数据库直接提供，无需部署容器、无需维护连接池、
   无人对局时零成本（容器方案需常驻计费）。

3. **与既有的房间系统天然同构**
   房间状态（`rooms` 集合）与对局状态（`games_*` 集合）本就存在数据库中，
   客户端 watch 这些集合即可同时覆盖「房间座位变化」与「对局棋步同步」，
   无需为两者维护两套通道。

4. **上行仍走云函数，权威性不受影响**
   实时通道只负责**下行推送**；所有玩家操作（落子/翻格）都经云函数校验，
   因此「服务端权威、客户端无法作弊」的设计原则**并未因为选了 watch 而妥协**。

5. **本项目是第一阶段的 MVP（2 人回合制）**
   在 2 人、低频、回合制的约束下，WebSocket 的性能优势无法抵消其运维成本。

### 3.2 为什么保留 WebSocket 作为备选

watch 的三个硬伤在小规模场景可接受，但在以下演进方向会变成阻塞：

| 硬伤 | 影响 | 触发切换的条件 |
| :--- | :--- | :--- |
| **每客户端 ≤ 5 个 watch 连接** | 多人游戏中若同时 watch 房间 + 对局 + 聊天等多个集合，会触顶报错 | 需要同时监听 > 5 个集合 |
| **延迟与最终一致性** | 无法做「实时抢答」「限时抢位」等强时序玩法 | 需要 < 100ms 或严格有序 |
| **对局文档对客户端可读** | 寻机头的 `heads`/`cells` 若同集合存放，客户端技术可读（需拆表或换通道） | 需要状态完全服务端私有 |

### 3.3 关于寻机头敏感数据的处理

本阶段的设计已在**架构层面**做了防护：

- 客户端**只通过 `planehunt_flip` 逐格查询结果**，业务代码里没有任何读取 `heads`/`cells` 的路径；
- 布局生成在服务端（`startGame` 云函数），客户端不参与；
- 客户端只接收 `ph.flip.result`（单格内容），拿不到完整布局。

**残留风险**：若 `games_planehunt` 集合权限为「所有用户可读」，
攻击者可用开发者工具直接查询该集合拿到 `cells`。

**两种缓和方案**（第二阶段实施其一）：

| 方案 | 做法 | 成本 |
| :--- | :--- | :--- |
| **A. 敏感字段拆分**（推荐，改动小） | 把 `heads`/`cells` 移到独立集合 `games_planehunt_secret`，权限设「仅管理端可读写」；客户端只 watch 非敏感的对局集合 | 低（服务端加一个集合 + 客户端 `WxNetSyncService` 只 watch 公开集合） |
| **B. 切 WebSocket** | 对局状态完全保留在服务端内存，客户端只收「翻格结果」消息 | 中（需新建云托管服务） |

> 本项目推荐**方案 A**：以最小改动消除风险，且保留 watch 的低成本优势。

## 4. 实施要点（第二阶段）

### 4.1 watch 方案实施要点

```ts
// WxNetSyncService 核心实现骨架
async connect(roomId: string): Promise<void> {
    // 1) 上行：云函数
    //    客户端 send() → wx.cloud.callFunction({ name: 'gomoku_move' | 'planehunt_flip' })

    // 2) 下行：watch 对局集合
    this._watcher = wx.cloud.database()
        .collection(gameCollection)          // games_gomoku / games_planehunt
        .where({ roomId })
        .watch({
            onChange: (snapshot) => {
                // 把快照转成协议消息，交给业务层
                this._dispatchFromSnapshot(snapshot);
            },
            onError: (err) => {
                console.error('[WxNetSync] watch error', err);
                this._setStatus(NetStatus.RECONNECTING);
                // 触发全量对账
                void this.reconnect();
            },
        });
}
```

**必须处理的三个坑**：

| 坑 | 现象 | 处理 |
| :--- | :--- | :--- |
| **连接数配额** | 报「超出最大连接数」 | 离开房间/进入对局时 `close()` 旧 watcher；全应用同时最多 5 个 |
| **只推增量** | 断线期间棋步永久丢失 | `reconnect()` 必须调 `getRoomState` 拉全量并做 diff 补偿 |
| **权限静默失败** | 无报错也无回调 | 集合权限设为「所有用户可读」；上线前务必验证回调有数据 |

### 4.2 切换到 WebSocket 的实施要点

若后续决定切换，改动面**被刻意限制在单文件**：

```
需要改：assets/scripts/core/services/wx/WxNetSyncService.ts  （只此一个文件）
不需要改：
  - 所有游戏逻辑（GomokuGame / PlaneHuntGame）
  - 所有协议定义（Protocol.ts）
  - 所有 UI
  - 所有房间逻辑（IRoomService 接口签名不变）
```

这是因为第一阶段就把「游戏 ↔ 网络」的边界收敛到了 `INetSyncService` 接口上。
WebSocket 实现只需：
1. `wx.connectSocket({ url: `${AppConfig.REMOTE_SERVER}/ws?roomId=...` })`
2. `socket.onMessage(res => this._dispatch(JSON.parse(res.data)))`
3. `socket.onOpen/onClose/onError` → 维护 `NetStatus`
4. 上行仍通过 socket 发送（但**服务端仍需二次校验**，不能信任客户端）

---

## 5. 结论摘要（一句话）

> 本项目为**2 人回合制**小游戏，消息低频、延迟容忍度高、追求零运维与低成本，
> 因此第二阶段采用 **云数据库实时数据推送（watch）+ 云函数权威校验**；
> 上行操作全部经云函数校验以保证服务端权威，与选型无关；
> 寻机头敏感布局通过「**敏感字段拆表**」消除可读性风险；
> 若未来演进到多人高频或强时序玩法，再切换**云托管 WebSocket**
> —— 由于网络层已收敛到 `INetSyncService` 单接口，切换成本被限制在单文件内。
